# 业务图解：先让读者懂，再让页面好看

唯一验收标准是：没参与过这件事的人，读完能复述问题、做出选择、说出失效条件。字段、图表和动画都只是工具，不是目标。

## 三层模型

| 层 | 必须回答 | 验收 |
| --- | --- | --- |
| 事实 | 这是真的吗，适合当前场景吗 | 关键结论有来源；建议有约束、代价与反证 |
| 理解 | 读者会在哪里想错，为什么 | 费曼稿讲通；所选机制直接纠正具体误解 |
| 行动 | 读完能决定或做什么 | 选项、代价、可逆性清楚；teach-back ≥ 4/5 |

先读 [事实门禁](references/facts.md) 与 [教学方法](references/teach.md)。视觉与浏览器验收读 [visual-verification.md](references/visual-verification.md)。

## 四步流程

### 1. 定问题、读者与证据边界

只回答一个核心问题。写清读者已经知道什么、读完要决定什么，并用 [证据台账](templates/evidence.md) 绑定代码、文档、commit、测试、日志或指标。没有指针的内容只能标为推断或假设。至少做一次反证搜索；历史意图不明时标“需要确认”，不把风格差异判成缺陷。

### 2. 写 100 字费曼稿并确认

先做页面外的硬门禁：用不超过 100 字、无内部术语的话说明“谁，在什么前提下，发生什么，为什么，结果是什么”。把稿子交给用户纠正后再做页面；讲不通就补证，不用图表或动画掩盖。

### 3. 按读者卡点搭结构

每块采用“可能的误解 → 为什么错 → 支持纠正的证据”。典型顺序是：结论与决策问题、具体实例、误解纠正、时序或因果机制、近误对比、历史与边界、选项与代价、teach-back。按实际卡点合并，不凑章节。

费曼稿、证据台账、teach-back 必选；其余机制至少选两个，且各自对应一个失败模式。例子负责具体，动画只负责状态转换、因果链、时序或单变量对比。没有状态变化、caption 和最终静态状态的动画直接删除。

### 4. 双层验收与盲测

页面旁创建 `content.json`，遵循 [六字段契约](references/manifest-schema.md)；不为填字段编造内容。运行：

```bash
python scripts/audit_explainer.py --page /absolute/path/index.html --manifest /absolute/path/content.json
```

再按视觉门禁实测桌面、375px、键盘、控件与减少动态效果。最后用 [teach-back 模板](templates/teachback.md) 让未看源码的读者回答概念、对比、反例、决策、边界五题；≥ 4/5 才通过，并用 [评分表](templates/scorecard.md) 记录。自动审计不能代替盲测。

## 反面清单

不强制字段、示例数量、动画或播放器；不做猜谜式揭晓和装饰性动效；不写无来源事实、无适配论证的建议或虚构场景；不新建第二套设计系统；不把“生成 HTML”当作理解已发生。

交付时区分“静态通过”“浏览器通过”“盲测通过”和“仍需人工确认”，提供可打开页面及仍存在的证据缺口。
