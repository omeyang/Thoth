## 1. 证据和事实边界

- 当前行为优先核当前代码和真实调用方；历史行为使用冻结版本，不用当前 HEAD 静默替代。
- 文档候选、旧重构产物和通用经验只能提供线索，不能独立证明线上合同。
- 真实需求只能来自旧行为、已批准设计/裁决、可复现缺口或当前人工指令。
- 示例中的角色、数值和事件若是为了说明机制而构造，必须明确标注为示例；不得虚构生产事故、监控数据或实际执行结果。
- 把“尚未核验”写出来，不使用“显然”“一定”“完全”“零风险”等超出证据的措辞。
- 风险示例不等于已发生事故；静态推断不等于测试已运行；组件测试不等于生产场景通过。

## 2. 场景与易混淆场景

先定义场景，再选择处理路径。至少回答：

- 谁发起：用户、运维、调度方、服务进程、外部写入方；
- 为什么发生：业务增长、计划维护、故障、恢复、扩容或其他实际原因；
- 发生前什么是成立的；
- 谁改变状态，改变什么；
- 调用方、数据、消息和运维侧看到什么；
- 失败、取消、重复、乱序和结果不明分别如何处理。

### 易混淆场景对照模板

| 场景 | 相同表象 | 关键差异 | 正确处理 | 误用的后果 |
| --- | --- | --- | --- | --- |
| 当前场景 |  |  |  |  |
| 相邻场景 A |  |  |  |  |
| 相邻场景 B |  |  |  |  |

不要只按名称区分。例如“故障”和“主动迁移”都可能表现为服务不可用；真正区别是有没有另一个写者准备接管。

### 场景排除

每个被排除场景都要说明：

- 它与当前场景的相似点；
- 为什么本页不适用；
- 它应该走哪条已有路径；
- 如果硬套当前方案，会改变什么业务结果。

不得借“明确不做”隐藏当前场景必需的直接依赖。

## 3. 示例写作

示例必须包含具体角色、触发事件、动作、可观察结果和影响。优先使用“租户 A 在某场景发生某事件”的真实业务结构。

至少提供以下一种组合：

- 正常示例 + 失败示例；
- 错误示例 + 正确示例；
- 多个覆盖不同触发条件的示例。

好示例应让读者不用记住前文术语，就能从当前画面看出对象、动作和结果。一个页面可以有多个示例，但不得为了凑数重复同一情况。

### 示例核验

- 数值要算得清，前后状态一致；
- 角色不能在示例中途无解释地改变；
- 每个结果必须能由机制推出；
- 示例中的成功点不能越过文档规定的完成条件；
- 正确示例不能靠隐藏失败或省略关键步骤显得简单；
- 错误示例必须真实暴露机制，而不是把正确做法故意写得愚蠢。

## 4. 历史、影响和决策

### 历史

重构页面必须回答：

1. 历史系统怎样运行；
2. 为什么当时没有这个特定问题；
3. 现在新增了什么前提或参与者；
4. 哪些旧问题不能误称为新引入；
5. 哪些旧行为必须保持。

“历史上没有这个问题”只针对当前问题，不表示历史系统没有其他缺陷。

### 影响

按对象列影响：数据、调用方、查询、消息、存储、运维、恢复和审计。写清直接/间接、范围、可观察表现和是否可逆。不要只说“影响稳定性”。

### 人工决策

决策页必须让读者能回答：

- 要决定的具体问题是什么；
- 为什么现有证据不足；
- 谁有权决定；
- 每个选项改变什么业务结果、权限或责任；
- 选择后如何撤销或恢复；
- 还缺哪份证据。

不要把实现细节、个人偏好或纯命名问题升级成人工审批。

## 5. 简洁语言

- 优先短句和主动语态，一段只表达一个结论。
- 先写业务语言，再考虑是否需要技术名称；能绕开的术语不写。
- 必须使用的术语在首次出现处用普通语言解释；后续保持一致。
- 不为“高级感”创造名词，不堆叠同义词，不使用抽象动词代替实际动作。
- 不写“闭环、赋能、抓手、体系、编排、链路”等空泛词，除非它们有明确且必要的业务含义。
- 少用“由于……因此……”长链；拆成可逐项核验的句子。
- 避免重复标题、正文和图注讲同一句话。

## 6. 自洽检查

交付前逐项回答：

- 场景前提是否始终一致；
- 示例状态是否随步骤正确变化；
- 原因和结果是否被倒置；
- 正确与错误示例是否使用相同初始条件；
- 影响范围是否超过证据；
- 历史结论是否只覆盖当前问题；
- 决策选项是否互斥且覆盖真实可行路径；
- 动画、文字和图注是否表达同一事实；
- 是否有任何一段只能凭作者内部知识才能看懂。
