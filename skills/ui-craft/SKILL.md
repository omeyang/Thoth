# UI Craft

把界面当作信息设计，而不是组件拼装。先让内容有秩序，再让它有性格；最后用真实画面证明，而不是凭代码想象效果。

## 原则

1. **主题决定形式**：从内容、读者和主要任务提取视觉语言，不先选流行模板。
2. **内容先于装饰**：讲解页先建立心智模型；工具页首屏直接呈现工作区；只有说服型页面才需要大型开场。
3. **一个记忆点**：把大胆留给一个构图、图解或关键交互，其余保持安静。
4. **沿用已有系统**：存量项目先读现有 tokens、组件和页面；保留品牌与业务行为，不另建平行主题。
5. **真实且完整**：不编造数据、截图、评价或在线能力；覆盖加载、空、错误、长文本和禁用状态。
6. **证据后交付**：静态检查不能替代截图，截图不能替代点击与键盘走查。

## 选择路径

| 任务 | 做法 |
| --- | --- |
| 已点名元素与改法的小修改 | 直接修改并检查目标视口，不启动完整设计流程 |
| 新建页面、整体改版、用户只说“丑/不高级” | 执行完整流程 |
| 技术设计或代码讲解页 | 完整流程，并读 [技术讲解页](references/technical-explainers.md) |
| 品牌、作品集、发布或展览页 | 完整流程，并读 [品牌展示与动态作品墙](references/showcase-and-media.md) |
| 提供 Figma URL、节点选择或设计导出 | 读 [Figma 设计实现](references/figma-implementation.md)；无视觉证据时不宣称 1:1 还原 |
| 提炼、建立或维护项目设计规范 | 读 [语义化设计系统](references/design-system.md)，区分事实、建议和未知 |
| 只读评审 | 收集证据，按影响排序给建议；不改文件 |
| 截图/参考站还原 | 先分清“精准还原”还是“借鉴方法”；不复制无关品牌与内容 |

信息足够时不要反复询问。缺少的事实若能合理推断，记录假设并继续；只有会改变核心方向的未知才集中问一次。

## 1. 取证与内容建模

读取与任务相关的现有页面、样式变量、组件、资产及 `DESIGN.md`。有参考站或截图时，观察实际画面并记录：

- 首屏优先级、信息密度与阅读顺序；
- 字体角色、色彩比例、间距、边界和图像处理；
- 关键交互及其反馈；
- 哪些特征服务主题，哪些只是表面装饰。

讲解页先写“读者 → 已知道什么 → 看完能解释/决定什么”，再列内容因果链。不要用视觉动画掩盖逻辑缺口。

## 2. 写紧凑设计契约

写代码前形成一段可检查的契约；新项目或用户要求沉淀时写入 `DESIGN.md`，否则放在工作说明中。至少包含：

```text
北极星：一句话说明这个界面为何适合该主题，而非任何主题。
读者/任务：谁在这里完成什么。
视觉主角：一个最重要的图形、文字、媒体或交互。
色彩：4–6 个语义角色及比例，不只罗列好看的色值。
字体：标题/正文/代码的字体、字重、字号阶梯与行长。
构图：首屏 ASCII 线框、内容宽度、对齐、密度与移动端重排。
形状：边框、圆角、阴影的使用条件。
动效：一个有目的的编排时刻；列出不动的部分。
反目标：本页明确不要出现的 3 件事。
```

如果这份契约换一个产品仍完全成立，就重做。用户明确要求比较方向时，候选必须在构图、字体、色彩和主视觉上有实质差异，不能只换配色。

视觉细则按需读 [视觉语言](references/visual-language.md)；需要持久化或从现有实现提炼规范时，遵循 [语义化设计系统](references/design-system.md)，记录精确值、功能角色与 `Known Gaps`。

## 3. 建立语义系统再实现

- 先定义 `background`、`surface`、`foreground`、`muted`、`accent`、`border`、`focus` 等语义 tokens，再写组件。
- 使用项目当前框架和组件库；无项目时优先少依赖、可直接预览的实现。
- 让网格服务内容：工具与讲解页优先稳定列、清晰标签和可读行长；避免把每段都装进相同卡片。
- 用真实内容做首版。代码、图表、导航和示例必须是页面实际主题的一部分。
- 图片选择可靠来源并保留许可/来源；装饰图不得冒充真实产品截图。
- 从窄屏到宽屏检查重排，不只缩小桌面布局；不用 `overflow-x: hidden` 掩盖溢出。

## 4. 设计交互，而非只设计静止画面

为主要操作实现默认、悬停、按下、焦点、禁用、加载、成功和失败状态。动效先回答“是否必要、目的是什么、多久出现一次”。

- 高频操作立即反馈；普通 UI 过渡通常控制在 100–250 ms，避免缓慢入场阻碍阅读。
- 进入用偏 ease-out 的曲线；连续移动用 ease-in-out；只给需要循环的运动用 linear。
- 优先 `transform` 与 `opacity`，不写 `transition: all`；可中断交互使用可重定向的过渡。
- 弹出层从触发点附近出现；按下反馈轻，不让布局跳动。
- 支持键盘、触控和 `prefers-reduced-motion`；手势必须有按钮/键盘替代。

细则读 [交互与无障碍](references/interaction-accessibility.md)。

## 5. 审计与真实画面验收

对 HTML/CSS 或含内联样式的页面运行本目录脚本（Python 3 标准库）：

```bash
python <skill>/scripts/audit_ui.py --path /absolute/path/to/page-or-project
python <skill>/scripts/audit_ui.py --path /absolute/path --strict --json
```

静态审计只发现它能证明的问题。随后用真实浏览器完成：

1. 在桌面与约 375–390 px 手机视口截图并实际查看；检查首屏、整页层级、溢出、遮挡、行长和对比度。
2. 点击每个主要控件，验证状态变化；走通键盘路径，检查焦点可见与弹层焦点恢复。
3. 检查控制台异常、资源 404、长文本、空/错误状态和减少动态效果模式。
4. 对照设计契约做“减法”：删除不传达信息的徽章、眉题、编号、渐变、阴影和重复文案。
5. 修复后重跑受影响检查；未执行的项目明确写“未验证”。

评审顺序与记录格式见 [评审清单](references/review.md)。

## 反模板检查

除非主题或用户明确要求，不把以下默认值当作设计：

- 紫蓝渐变、发光球、玻璃拟态和每张卡片同款柔阴影同时出现；
- 所有内容居中，上面放无信息量的全大写 eyebrow；
- 标题只把一个词换成斜体或强调色；
- 每个区块都有 `01 / 02 / 03`，内容却不是步骤或时间线；
- 所有按钮都做成胶囊，所有图标都放进圆角色块；
- 工具页用巨大口号把真实工作区挤到首屏以下；
- 每段滚动都上浮淡入，每次悬停都浮起；
- 用虚构 KPI、客户评价和“效率提升 10 倍”填补空白。

这些不是永久禁令。若它们来自内容且与整体方向一致，可以有理由地使用。

## 交付

说明实际完成的页面/修改、设计方向和验证范围，提供可打开的预览。区分“静态审计通过”“浏览器已验证”和“仍需人工确认”，不把审美评分伪装成客观基准。
