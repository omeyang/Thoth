# 影响链、调用方与假设证据

改动前先回答“谁会受到影响”，再讨论方案优劣。不能只读准备修改的函数，也不能用没有证据的极端假设替代现实业务分析。

## 三条必须核查的链

| 链 | 要还原的内容 | 可用证据 |
| --- | --- | --- |
| 数据流转链 | 谁产生数据、经过哪些接口/队列/存储、谁消费、何时可见、修改后语义是否变化 | 生产者与消费者代码、接口文档、Schema、消息记录、日志、测试 |
| 函数调用链 | 谁调用目标函数、目标又调用谁、直接和间接调用方分别依赖什么行为 | 代码检索、引用定义、调用方测试、动态注册/配置、运行时调用记录 |
| 接口调用顺序 | A/B 等接口的先后、并发、超时、重试、取消和结果不明时各自处于什么状态 | 编排代码、时序图、契约、链路追踪、集成测试 |

不要只画一条理想路径。失败、重试、重复、乱序和结果不明会改变影响范围时，也要核查对应分支。

## 改动影响谁

对准备修改的点逐项列出：

1. **直接调用方**：谁直接调用或读取它，依赖哪些输入、输出、顺序和异常语义。
2. **间接调用方**：谁通过上层服务、消息、缓存或存储间接受影响。
3. **数据上下游**：谁产生数据，谁消费数据，数据由哪个团队或系统负责。
4. **明确不受影响者**：哪些路径不经过这个改动，依据是什么。
5. **未知范围**：动态调用、反射、配置、外部系统或缺少可观测性导致无法确认的部分。

不能只写“影响接口 A”。要写成“调用方 C 在顺序 S 下依赖字段 F；改动后 F 的语义改变，因此 C 的判断结果可能改变”，并给出来源。

## 接口不是天然的脏数据来源

接口属于外部团队或兄弟部门，只说明责任边界，不证明它不可靠。不得默认接口 A 会故意产生脏数据、相反数据或恶意行为。

对接口行为的判断分三级：

| 级别 | 需要的内容 | 能怎样使用 |
| --- | --- | --- |
| 已观察 | 实际代码、功能行为、日志、追踪或测试证明会出现 | 可作为现实场景与决策依据 |
| 合同允许 | 文档或接口契约明确允许该结果，即使当前没观察到 | 可作为有依据的边界场景 |
| 纯假设 | 只有“理论上可能”，没有代码、文档、功能或运行证据 | 只能标为假设，不得作为否决方案的主要依据 |

发现疑点时先查接口实现、文档、正常功能、测试与真实记录，或向责任方确认。不能把“不是本团队维护”当成负面证据。

## 假设必须与决策成比例

理论可能性不等于现实决策场景。无证据的极端假设不能用来推翻方案，也不能让方案比较失去意义。

如果 A、B 方法只在某个假设下表现不同，先问：

- 这个假设有现实证据吗？
- 当前接口合同允许吗？
- 真实调用链会走到这里吗？
- 若把该假设移除，A、B 的实际差异是什么？

如果移除假设后两者没有实质差异，就明确写“该假设不构成 A/B 的决策依据”。例如讨论盖房方法时，“地球明天爆炸”若没有证据，就不是选择盖房方法的有效变量。

低概率但高后果的风险可以单列为待核验边界，但不能伪装成已发生事实，也不能代替对正常业务链路的分析。
