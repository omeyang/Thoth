# 业务问题图解

先证明内容真实、完整、易懂，再制作页面。页面是理解与决策工具，不是把技术报告换成更漂亮但更难懂的包装。

## 不可妥协的原则

1. **业务真实**：从当前代码、真实调用方、批准文档、日志和人工裁决取证；不得编造事故、指标、角色、协议或因果关系。
2. **讲人话**：优先使用读者熟悉的业务语言；绕开或解释术语，不创造新名词，不靠复杂措辞制造深度。
3. **场景清楚**：写清谁、在什么前提、发生什么事件、产生什么结果；把易混淆场景并列对比，不混用处理路径。
4. **逻辑闭合**：按“触发 → 机制 → 可观察结果 → 影响 → 决策/处置”建立因果链；事实、风险示例、推断和假设必须分开标记。
5. **历史与影响完整**：重构须说明历史行为、历史上为何没有该问题、现在改变了什么；影响写清对象、范围和后果，不用“影响很大”代替分析。
6. **视觉服务理解**：图表和动画只表达文字已经核验的关系；不得为了好看增加场景、虚构数据或扩大风险。
7. **可验证交付**：内容审计、真实浏览器、桌面/手机截图、交互、控制台、404 和减少动态效果均须实际通过；不得把“生成了文件”当作“已验证”。

## 执行流程

### 1. 明确读者与问题

从请求和现有材料确定：

- 读者是谁，已有何种背景，读完后应理解或决定什么；
- 页面回答的一个核心问题是什么；
- 哪些内容明确不在本页范围内。

信息已在请求中时不要重复询问。缺少会改变业务结论的事实时，先补证；不要靠页面掩盖未知。

### 2. 建立证据台账

至少读取当前实现、真实调用方、直接设计/决策和适用历史。每条关键结论记录来源、版本、事实及证据状态。区分：

- 已观察到的当前事实；
- 已核验的历史或文档合同；
- 可复现的故障/反例；
- 仅为说明机制的假设示例；
- 尚未验证的推断。

任何示例都必须能追溯到机制证据；明确标注“风险示例，非线上事故”，不得把假设写成事实。

### 3. 绘制场景地图

每个场景写清：

| 字段 | 必答内容 |
| --- | --- |
| 触发者 | 谁发起或哪个系统事件触发 |
| 前提 | 发生时必须已经成立的条件 |
| 事件 | 实际发生什么，不用抽象标签代替 |
| 状态变化 | 前后状态及状态推进者 |
| 外部结果 | 调用方、数据、消息和运维侧能看到什么 |
| 处理路径 | 为什么走这条路径，而非相邻场景的路径 |

随后列出易混淆场景：相同表象、关键差异、处理差异、误用的后果。不能用名称区分场景，必须用业务条件区分。

### 4. 建立问题与影响链

按以下顺序检查逻辑：

`业务前提 → 具体事件 → 失效机制 → 可观察问题 → 直接影响 → 传递影响 → 影响范围`

每一步都要能回答“为什么”。没有证据的箭头标为推断或删除。明确：

- 哪些对象直接受影响；
- 哪些下游或运维责任被传递影响；
- 哪些对象明确不受影响；
- 是已发生、已复现，还是可能发生；
- 影响是单租户、单节点、单请求、单 Pod，还是其他有证据的范围。

### 5. 解释历史与决策

有历史系统时，回答：

- 原来如何处理；
- 原来为何没有这个问题，不能只说“旧系统简单”；
- 新架构或业务变化引入了什么新前提；
- 哪些是继承行为，哪些是批准的新行为。

需要人工决策时，只呈现会改变业务结果的选项，写清决策所有者、所需证据、选项后果和撤回/恢复边界。不得把纯内部实现选择包装成人工审批。

### 6. 设计内容与演示

先写内容大纲，再选择视觉。典型顺序：

1. 一句话结论和具体场景；
2. 场景与易混淆场景对照；
3. 主图或动画演示；
4. 至少两个贴切示例，或一组正确/错误示例；
5. 问题为何发生；
6. 历史差异；
7. 影响范围与对象；
8. 需要决策或执行的下一步。

可以合并相邻内容，但不得重复讲同一结论。动画只用于顺序、状态转换、因果或对比确实更清楚的场景。提供上一步、下一步、播放/暂停、重置和键盘操作；所有内容在静止状态仍完整可读。

视觉与已有文档/页面保持一致：先读取现有页面，复用颜色、字体、间距、圆角、图标和交互语义；没有既有样式时再定义简洁设计，不套用与项目无关的模板。

详细内容契约见 [references/content-quality.md](references/content-quality.md)，视觉与无障碍规则见 [references/presentation-accessibility.md](references/presentation-accessibility.md)。

### 7. 生成内容清单和页面

在页面旁创建 `content.json`，逐字段遵循 [references/manifest-schema.md](references/manifest-schema.md)。清单用于审计，不是额外文书；只保留本页实际使用的内容。

生成纯静态 HTML/CSS/JavaScript，不引入后端或虚构在线能力。页面使用用户语言，保留真实来源入口，并注明风险示例和未验证边界。

### 8. 执行双层验收

先执行内容/结构审计：

```bash
python scripts/audit_explainer.py --page /absolute/path/index.html --manifest /absolute/path/content.json
```

再在真实浏览器验证：

- 桌面和 375px 手机截图并实际查看；无横向溢出、遮挡和不可读文字；
- 主流程、正确/错误分支、每个按钮、导航和键盘操作均有实际结果；
- 播放可暂停、重置；`prefers-reduced-motion` 下无多余动画；
- 0 控制台错误、0 页面异常、0 HTTP 错误/404；
- 记录请求数、页面大小和关键交互结果；
- 删除验证临时文件，不留下后台服务器。

失败时先修复并重跑；不得删除断言、隐藏错误或把未执行写成通过。

### 9. 交付与续接

提供可打开的页面路径/预览，并简述实际验证范围。明确仍存在的事实缺口和需要人工决定的事项，不声称发布上线，除非另有发布流程实际完成。

收到读者反馈后，先判断是内容模型错误、场景遗漏、语言不清还是视觉问题；修改后重跑相同双层验收。
